# Continuation Debug Context

This file is a handoff document for the theorem-continuation debugging work in `proof-compass`.

It is written to give a new Codex session enough context to continue without relying on chat history.

## 1. High-level goal

The long-term goal is to generate training data that helps reduce Mathlib hallucinations in Lean proofs.

The practical motivation is:

- The model often produces Lean proofs that mention nonexistent or malformed Mathlib theorem names.
- We want to understand that failure mode precisely.
- We want to build data and tooling that can later be used to reduce those hallucinations.

The specific subproject documented here is a continuation experiment:

- Take a successful proof generated by the model.
- Find a place where it correctly uses a Mathlib theorem in the proof.
- Cut the response immediately before that theorem occurrence.
- Ask the model to continue for a small number of tokens.
- Measure whether it reproduces the intended theorem name, picks some other valid theorem, hallucinates a theorem-like name, or does something else.

The underlying question is:

> If the model already got the proof right once, and we resume generation from the exact local context before a Mathlib theorem, how often does it still hallucinate the theorem name?

The expectation was that this should work much better than full proof generation, because it is a small local continuation task rather than a full theorem-proving task.

## 2. Why this matters

The experiment is trying to isolate theorem-name selection from the rest of proof construction.

This matters because:

- Full proof generation mixes many failure modes together.
- A failed full proof does not tell us whether theorem recall itself is broken.
- If local continuation before a theorem is already unreliable, then theorem hallucination is a much deeper issue than simple proof-search failure.

The experiment is also intended to be lightweight:

- no Lean verification
- short continuations only
- reuse existing successful outputs

That makes it fast enough to iterate on.

## 3. Current experiment design

The current continuation experiment lives in:

- `rag_experiments/run_msc180_v3_theorem_continuations.py`

It uses:

- Source non-CoT verified outputs:
  - `rag_experiments/outputs/20260301_msc180-v2_deepseekv2_7b_lean4-15_verified.json`
- Compact Mathlib theorem-name index:
  - `rag_experiments/data/mathlib_theorem_name_index.json`

It produces:

- `rag_experiments/outputs/20260306_msc180-v3-theorem-continuations_deepseekv2_7b_lean4-15.json`

The analyzer scripts are:

- `rag_experiments/analyze_msc180_v3_theorem_continuations.py`
- `rag_experiments/analyze_msc180_v3_continuation_corruption.py`

### 3.1 Slot construction

The experiment mines a curated set of successful non-CoT attempts from the MSC-180 v2 run.

Only a fixed set of config/problem cells is used:

- `USABLE_SOURCE_KEYS` in `rag_experiments/run_msc180_v3_theorem_continuations.py`

For each successful attempt:

1. Find the `parsed_proof` inside `raw_output`.
2. Look inside the proof body after `:= by`.
3. Scan identifiers.
4. Match identifiers against the Mathlib theorem index.
5. Keep the first occurrence of each distinct matched theorem in that attempt.
6. Create one continuation slot per theorem occurrence.

This produces exactly:

- `95` slots

Each slot stores:

- source key
- attempt index
- target theorem full name
- target theorem token as it appears in the proof
- exact visible prefix text before that theorem occurrence
- tokenized prefix ids
- cut metadata

### 3.2 Generation setup

The current runner uses:

- model: `deepseek-ai/DeepSeek-Prover-V2-7B`
- attempts per slot: `8`
- max new tokens: `24`
- temperature: `1.0`
- top_p: `0.95`
- micro-batch size: `8`

So the full run is:

- `95` slots
- `8` continuations each
- `760` short generations total

### 3.3 Classification

Each continuation is classified into one of:

- `exact_match`
- `other_valid_mathlib_theorem`
- `hallucinated_theorem_like_name`
- `incomplete_identifier`
- `no_theorem_like_identifier`

The first theorem-like identifier in the continuation is what gets classified.

Important limitation:

- The classification index is theorem-only, not all Mathlib declarations.
- So some valid non-theorem constants may still be counted as hallucinations.

## 4. Original motivation for this exact design

This design came from earlier exploration of the non-CoT MSC-180 run.

We found that:

- There are many successful attempts that explicitly use Mathlib theorem names.
- There are also many failed sibling attempts on the same problems that hallucinate nearby Mathlib names.

This made continuation probing attractive, because it lets us ask:

- given the exact context from a successful proof, what does the model do locally at the theorem boundary?

The experiment intentionally uses the original visible `raw_output` context because the user wanted the model to see exactly the same kind of text it originally saw, including:

- prompt wrapper
- hints
- examples
- markdown/code fences
- earlier generated text in the same response

That choice was deliberate.

We explicitly did **not** want to switch to a cleaned proof-only prompt, because that would no longer be the same local continuation problem.

## 6. What was broken earlier

Several independent bugs and confusions happened during development.

This section is important because it prevents re-investigating already-resolved issues.

### 6.1 Stale output reuse

Earlier versions of the runner silently resumed old JSON outputs.

That caused major confusion because:

- the code was changed
- the output filename stayed the same
- the runner skipped already-filled slots
- analyzers were then run on stale data

This is now fixed by:

- top-level `__meta__`
- run metadata validation
- schema versioning
- refusal to resume incompatible outputs

### 6.2 Wrong char-cut to token-cut alignment

An earlier version tried to map a text cut to token boundaries using offset mappings.

That caused severe bugs:

- some prefixes were cut far too early
- saved cut metadata did not match expectations
- the resulting continuations were garbage

That offset-based logic was removed.

The current runner uses:

- exact visible-text truncation
- direct tokenization of that exact prefix text

### 6.3 Local vs VM environment mismatch

At one point the local environment and the GPU VM differed:

- local: `transformers 4.57.6`, `tokenizers 0.22.2`
- VM: `transformers 5.3.0`, `tokenizers 0.22.2`

This produced confusing results:

- same prefix text
- same cut chars
- different token counts

That mismatch is now resolved in the local repo venv:

- local now also uses `transformers 5.3.0`
- local still uses `tokenizers 0.22.2`

After matching versions, the current output file became fully consistent with the current runner.

### 6.4 Analyzer overcounting

Two analyzer issues were found and fixed:

1. `analyze_msc180_v3_theorem_continuations.py`
   - counted `__meta__` as a fake 96th slot

2. `analyze_msc180_v3_continuation_corruption.py`
   - counted any appearance of ```` ``` ```` as a restart
   - this wrongly classified many normal endings that simply closed a code fence

These are fixed now.

## 9. The most important remaining issue

This is the key technical finding at the moment.

Under the current environment:

- `transformers 5.3.0`
- `tokenizers 0.22.2`

the DeepSeek tokenizer decode path is emitting raw markers like:

- `Ġ`
- `Ċ`

instead of normal spaces/newlines.

This was verified directly.

Example:

- token ids corresponding to something like ` apply Eq.symm`
- `tokenizer.decode(...)` returns:
  - `'ĠapplyĠEq.symm'`

This is not just an analyzer bug.

It means the actual saved continuation strings can contain raw token-boundary markers.

That explains a large fraction of the remaining artifact reports.

### 9.1 Quantified effect

If we normalize only:

- `Ġ -> " "`
- `Ċ -> "\n"`

before applying the corruption rules, then:

- total corrupted attempts drop from `563` to `401`
- artifact-marker count drops from `304` to `35`

This is a major shift.

So at the current stage, the runner is internally consistent, but the decode path is still producing an unnatural text representation of the continuation.

That is now the most likely remaining technical bug.

## 10. Why the project is changing direction

At this point the continuation experiment is still too entangled for clean debugging.

Too many things are mixed together:

- source MSC-180 outputs
- theorem extraction from successful proofs
- prompt reconstruction assumptions
- tokenizer version issues
- decode representation issues
- analyzer heuristics

Even though several bugs were fixed, the remaining uncertainty is still too high.

So the decision is:

> Stop trying to fully debug the MSC-180 continuation setup directly.

Instead:

> Build a smaller, controlled experiment harness that isolates the tokenizer/generation/continuation issues directly.

This was explicitly discussed and agreed on.

## 11. New direction: controlled continuation experiments

The next phase should be a clean, standalone debugging setup.

It should not depend on MSC-180 or theorem extraction at first.

The goal is to understand the mechanics precisely:

- what token ids are produced
- what decode does
- whether `decode -> reencode` changes anything
- whether exact continuation from saved token ids behaves as expected
- whether text-prefix continuation and token-prefix continuation differ
- whether whitespace-boundary cuts matter

### 11.1 What the new harness should save

For every trial, save all of the following:

- prompt text
- prompt token ids
- prompt token strings if useful
- full generated token ids
- full decoded output
- continuation token ids after the cut
- continuation decoded text
- generation params
- model id
- tokenizer path
- `transformers.__version__`
- `tokenizers.__version__`
- cut metadata

This will make future debugging much easier because the run will contain everything needed for post hoc inspection.

### 11.2 Controlled tests to run

The recommended test suite is:

#### Test A. Token roundtrip fidelity

Generate a completion once and save:

- prompt token ids
- full output token ids
- decoded full output

Then compare:

- original full output token ids
- tokenizing the decoded full output again

This answers:

- is `decode -> reencode` lossy for this model in practice?

#### Test B. Exact continuation fidelity

From a generated sample:

1. choose a cut position
2. continue generation from the exact prefix token ids

Then compare:

- the next tokens to the original sampled continuation

This should first be done with deterministic generation if possible.

This answers:

- does exact prefix-token continuation behave like interrupted generation?

#### Test C. Text-prefix vs token-prefix

For the same cut:

- continue from exact prefix token ids
- continue from retokenized text prefix

Then compare outputs.

This answers:

- is re-tokenization the real culprit?

#### Test D. Decode representation

Take generated suffix token ids and test:

- `tokenizer.decode(...)`
- backend tokenizer decode
- any manual normalization

This answers:

- where exactly are `Ġ/Ċ` entering the pipeline?

#### Test E. Whitespace-boundary cuts

Create tiny controlled cuts:

- cut after `:= `
- cut after `apply `
- cut before a theorem name token with leading space
- cut at points with and without trailing whitespace

This answers:

- do whitespace-boundary cuts materially change continuation behavior?

### 11.3 Scope discipline for the new harness

The new harness should be:

- model-only
- no Lean verification
- no MSC-180 logic initially
- no theorem extraction logic initially
- small prompts
- few manually inspected examples

The idea is to debug the mechanics first, then return to MSC-180 once the basic continuation pipeline is trusted.

## 12. Strong recommendations for the next session

When continuing this work in a new Codex session:

1. Read this file first.
2. Confirm current environment versions:
   - `transformers`
   - `tokenizers`
3. Do **not** immediately patch the MSC-180 continuation runner again.
4. Build the controlled harness first.
5. Save token ids explicitly.
6. Treat decode behavior as a primary debugging target.

### 12.1 Things that are already known and should not be rediscovered

These are already established:

- stale output reuse was a real bug and is fixed
- offset-based token-boundary mapping was a bad approach and was removed
- current `20260306` output matches current runner logic exactly under matching library versions
- analyzer overcount from `__meta__` and bare closing fences is fixed
- the tokenizer decode path under `transformers 5.3.0` can emit raw `Ġ/Ċ`

### 12.2 Things that are still open

These are not yet resolved:

- why the `transformers 5.3.0` decode path behaves this way
- whether the correct fix is:
  - different decode usage
  - explicit normalization
  - another tokenizer config tweak
  - a different saved representation
- how much of the remaining bad continuation behavior is real model behavior vs text-representation artifact
